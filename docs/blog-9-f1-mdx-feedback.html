Issue 1 — category: "Event Pricing" is not in the schema enum (build will FAIL)

Build-blocker — Astro content-collection validation

The Astro content config at src/content/config.ts defines a strict enum for category:

category: z.enum(['Strategy', 'Pricing', 'Markets', 'Tools', 'Case Study'])

"Event Pricing" is not in that enum. Astro will throw a Zod validation error at build time and the post won't render at all.

Fix: Change to one of the valid values. The cleanest match for this piece is:

category: "Pricing"

("Strategy" would also work and matches Blog 7. "Pricing" is more literal — this post is explicitly an event-pricing playbook.)

Issue 2 — Hero image is a literal placeholder string (build will produce broken hero)

Build-blocker — placeholder unfilled

Frontmatter currently reads:

image: "/heroes/[hero-image-filename].webp"
imageAlt: "A split aerial view of Hard Rock Stadium Miami, Circuit of the Americas Austin, and the Las Vegas Strip at night..."

The literal string [hero-image-filename] will be requested by the browser as-is. Result: broken hero image on production + broken OG card.

Fix: RevFactor team will assign an actual hero. For now, leave a real file from public/heroes/ (e.g. clifftop-2400.webp, cliffside-2400.webp, or meadow-2400.webp) as a placeholder so the build doesn't break. The imageAlt is good and can stay once we generate the actual race-collage hero.

Issue 3 — Frontmatter slug and canonical will create /blog/blog/... URL duplication

Same bug we hit on FIFA post + Blog 7 v1 — known regression

Frontmatter currently has:

slug: /blog/f1-race-weekend-str-pricing-playbook
canonical: https://www.revfactor.io/blog/f1-race-weekend-str-pricing-playbook

Astro uses filename-based routing — the file src/content/blog/f1-race-weekend-str-pricing-playbook.mdx is automatically served at /blog/f1-race-weekend-str-pricing-playbook/. Adding a slug: prefixed with /blog/ double-prefixes it to /blog/blog/f1-race-weekend-str-pricing-playbook/.

Canonical is also auto-emitted by the BaseLayout from Astro.url. Hard-coding it in frontmatter is at best redundant; at worst it overrides the route Astro picked and creates a canonical mismatch.

Fix: remove both lines entirely. The Astro layout handles routing and canonical from the filename.

slug: /blog/f1-race-weekend-str-pricing-playbook     ← DELETE
canonical: https://www.revfactor.io/...               ← DELETE

Issue 4 — JSON-LD @graph duplicates everything the layout auto-emits (schema collision)

Same problem Muskan flagged on Blog 7 + FIFA — the layout-emitted entities are colliding with the MDX-defined ones

The blog layout (src/pages/blog/[...slug].astro) automatically emits, for every post:

  • Organization (with @id: #organization and the full sameAs + logo + description)
  • Person for Federico (with @id: #federico, 7+ sameAs URLs, jobTitle, knowsAbout array, alumniOf American Airlines, worksFor reference)
  • BlogPosting (with all the dates, author/publisher refs, isPartOf Blog, articleSection from category)
  • FAQPage (built from the frontmatter faqs: array)
  • BreadcrumbList

The F1 MDX @graph currently redefines all five of these with shorter, less-complete versions that fight the layout. The federico sameAs list in the MDX (3 entries) is missing 4 entries the layout publishes — Google ingests the smaller set and the entity graph fragments.

Worse: the MDX-defined BlogPosting has a different @id than the layout's (#article vs #blogposting), so Google sees TWO BlogPosting nodes for the same URL, with mismatched data on each. This is the same dup-schema warning Muskan flagged on Blog 7.

Fix: strip the entire @graph down to only what the layout doesn't already emit. The only block worth keeping is the ItemList ("Common F1 Pricing Mistakes"). The Table type isn't valid Schema.org and should be dropped or converted to an ItemList.

Replace the entire <script type="application/ld+json">...</script> block with just this:

Issue 5 — Manual ## Frequently Asked Questions section in the body duplicates the auto-rendered FAQ accordion

Will render the FAQ block twice on the live page

The blog layout reads the frontmatter faqs: array and auto-renders a styled accordion at the end of the article body. The MDX also has a manual ## Frequently Asked Questions H2 with 6 Q/A pairs hand-written into the body.

Result on the live page: two FAQ sections, identical content. Plus the manually written FAQs in the body wrap each question as ### Question H3s, which inflates the TOC by 6 extra entries the reader doesn't need.

Fix: delete the entire ## Frequently Asked Questions section from the body (the last ~30 lines before the file ends). The layout will render the styled accordion from the frontmatter automatically.

Issue 6 — UTF-8 mojibake (em-dashes saved as Latin-1)

Same chronic export issue we hit on Blog 7 v1 — needs a re-save as UTF-8 without BOM

Em-dashes (—) appear as the literal byte sequence â in several places. If committed as-is, the LIVE page renders those broken characters verbatim.

In the fileShould beLocation
price Miami, Austin & Las Vegas â what hosts should chargeprice Miami, Austin & Las Vegas — what hosts should chargetitle in frontmatter + body H1 echoes

Fix: re-save the file as UTF-8 without BOM. From command line:

Or in VS Code: bottom status bar → "UTF-8" → "Save with Encoding" → "UTF-8".
